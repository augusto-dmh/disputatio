# design — memoria-slice (slice 0.2)

## Approach

Same hexagonal shape as 0.1 (docs/architecture.md): the domain owns the review rules and a `Scheduler` port; infrastructure owns rs-fsrs, Postgres and AnkiConnect; the presentation stays translation-only. The import executes the ADR 0004 addendum once the owner decides — the design below assumes the recommendation (import), and the deletion path if rejected is described where it diverges.

**Scheduling.** `domain/review.rs` defines the review entities (`ReviewCard`, `Grade` = again/hard/good/easy, review-log entry), the pure rules (due filter, batch ordering), and the `Scheduler` port: `schedule(card, grade, now) -> (card state, review log)`. The port is sync and pure — no async, no IO. `infrastructure/fsrs.rs` implements it with **rs-fsrs 1.2 as a direct dependency** (Cargo.lock is tracked and committed): default FSRS parameters, desired retention 0.90, one scheduler instance per pool handle. Keeping rs-fsrs behind the port (not in domain) contains library churn and lets `fitness.py` enforce the boundary (`rs_fsrs` joins the domain-banned token list); chrono stays the precedent for allowed pure deps, but rs-fsrs is the *implementation* of a port, not a shared vocabulary.

**Memory-state reconstruction.** If history import is approved, each card's Anki review log is replayed through the scheduler in chronological order to arrive at the card's current memory state (deterministic, no ML runtime). The official `fsrs` crate with its optimizer would give trained weights but drags in a heavy toolchain for a one-time import — recorded as future work if the owner wants tuned weights.

**Queue due switch.** `DailyQueue.anki: AnkiStatus` is replaced by the internal due count (`due: u32`, kept cards due ≤ now, from the cards repo). The `AnkiGateway` port leaves the queue path; `AnkiStatus` and `AnkiHeaderDto` die. The **AnkiConnect module's fate follows the owner decision**: if import is approved it stays as a one-shot, user-invoked maintenance path (never runtime — ADR 0004 holds: nothing calls it unless the user presses Import in Settings); if start-fresh wins, `anki_connect.rs`, `AnkiGateway`, and their tests are deleted in the import task.

**Review flow.** Home keeps one queue answer: the header counts what's due, and a Memoria block offers "Review now" (shown when due > 0, "nothing due" otherwise). The reviewer is inline on Home (front → reveal → four grade buttons → next card, with i/n progress); a separate route is not worth it for one block. Grades go through `grade_card`; the batch through `list_due_cards(limit)` (default 20, oldest due first) so IPC stays bounded (payload rule).

**New commands** (registered in `collect_commands!`, `#[specta::specta]`, narrowed at the edge — no i64/u64 over IPC): `list_due_cards(limit) -> Vec<CardDto>`, `grade_card(card_id, grade) -> CardDto`, `import_anki() -> ImportSummaryDto`.

## Data model changes

Migration `0002_memoria.sql`, 0001 style (comments, CHECK constraints, TIMESTAMPTZ; BIGINT ids narrowed only at IPC). Draft:

```sql
CREATE TABLE cards (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    -- nullable: Anki-imported cards predate the vault index; narratio drafts (0.3) set it
    chunk_id BIGINT REFERENCES chunks (id) ON DELETE SET NULL,
    -- stable external key: the one-time import upserts on it (idempotent, like vault_path)
    anki_card_id BIGINT UNIQUE,
    deck TEXT,
    front TEXT NOT NULL,
    back TEXT NOT NULL,
    -- curation gate (architecture.md sketch): imports arrive pre-curated = kept;
    -- drafts (0.3) start as draft; killed cards never surface for review
    curation TEXT NOT NULL DEFAULT 'kept' CHECK (curation IN ('draft', 'kept', 'killed')),
    -- FSRS state — written only by the scheduler path (application/review.rs);
    -- f64/DOUBLE PRECISION because rs-fsrs Card carries stability/difficulty as f64
    stability DOUBLE PRECISION,
    difficulty DOUBLE PRECISION,
    -- learning | review | relearning (rs-fsrs State; NULL = never reviewed = new)
    fsrs_state TEXT CHECK (fsrs_state IN ('learning', 'review', 'relearning')),
    due TIMESTAMPTZ,
    last_review_at TIMESTAMPTZ,
    reps INT NOT NULL DEFAULT 0,
    lapses INT NOT NULL DEFAULT 0
);

CREATE TABLE reviews (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    card_id BIGINT NOT NULL REFERENCES cards (id) ON DELETE CASCADE,
    -- 1=again 2=hard 3=good 4=easy (FSRS ratings)
    grade INT NOT NULL CHECK (grade BETWEEN 1 AND 4),
    reviewed_at TIMESTAMPTZ NOT NULL,
    -- fsrs_state of the card BEFORE this review; NULL = first review
    state_before TEXT,
    -- rs-fsrs carries day counts as i64
    elapsed_days BIGINT NOT NULL DEFAULT 0,
    scheduled_days BIGINT NOT NULL DEFAULT 0,
    duration_ms INT,
    -- review-log import dedup: one Anki revlog row per card per timestamp
    UNIQUE (card_id, reviewed_at)
);

CREATE INDEX cards_due_idx ON cards (due);
```

New cards (imported without history) get `due = now()` at import, so the ordinary due query surfaces them as introductions — no separate "new queue". Owner: the scheduler service; nothing else writes `stability`/`difficulty`/`fsrs_state` or inserts `reviews` (architecture.md contract).

## Alternatives considered

- rs-fsrs types directly in `domain/` — rejected: the scheduler is the port's implementation, not a shared vocabulary like chrono; keeping it in infrastructure contains version churn and gives `fitness.py` a crisp line to enforce.
- `fsrs` crate (official, with optimizer) for trained weights at import — rejected for 0.2: heavy toolchain for a one-time job; replay through default parameters gives honest due state; revisit as a follow-up if retention tuning matters.
- Keep the AnkiConnect due total as a fallback header beside the internal count — rejected: two due sources make the one answer ambiguous, and ADR 0004 says Anki is never required at runtime after 0.2.
- Start fresh instead of importing history — the owner's call (draft addendum in the spec PR); this design recommends import because discarding the review log resets every card to new, which both lies about what the user knows and creates a day-one due wall.
- Separate Review screen/route — rejected for 0.2: the queue answer ("what do I study now") includes reviews; an inline block keeps one screen. Revisit if it crowds Home.

## ADR

[0004 — built-in FSRS review; Anki demoted](../../docs/adr/0004-built-in-fsrs-review.md) (*Accepted*). Its point-4 decision (import history vs start fresh) is drafted as a proposed addendum in this spec PR — recommendation: import; the owner decides before the import task merges. No new ADR needed for the port layout (docs/architecture.md already fixes it).
